00 — 认知

你不是在买工具,是在招人

如果你冲着"又一个 Cursor 平替"来用 Multica,那你会用错它——就像拿望远镜当显微镜,然后抱怨看不清细胞。

Cursor、Claude Code、Codex 解决的是怎么让一个程序员打字更快;Multica 解决的是另一个量级的问题:怎么让一个团队在没人盯着的时候继续运转。前者是工具,放大个人;后者是组织,放大协作。这两者的天花板,差着一个数量级。

差别就一句话:指派即执行。

在 Linear 里你把 issue 指派给张三,Linear 的活就干完了——它把名字贴上去,然后等张三离开 Linear、打开 IDE、自己干完、再回来手动改状态。规划和执行之间,隔着一条人肉搬运的鸿沟。

Linear · 规划层

一张精美的施工图

把"谁该干什么"安排清楚,然后等人离开它、去别处把活干完、再回来手动同步状态。规划与执行之间隔着一道墙。

Multica · 规划 + 执行

施工图 + 会施工的队伍

指派给 agent,它真的开始干:读 issue、翻历史、改代码、写结论、自己把状态翻成 in_review。你可以关电脑去睡觉。

所以 Multica 是 Linear 的上位替代:Linear 能做的它都能做,外加——被指派的那个对象,真的能把活干完。我们已经用它跑通一支 16 人的 AI 工程团队,正在做 Neuma-Agent(微信健康助手小程序),207 个 issue 已经啃下来 107 个。

这篇带你完成那个最关键的身份切换。

01 — 通用心法

从「操作者」到「指挥者」的 6 个动作

用错 Multica 最常见的姿势,就是把它当成"能跑后台任务的 Cursor"——开个 issue、丢一句模糊的话、然后像盯 IDE 一样守着它。这等于雇了一支团队,却用对待工具的方式对待它。下面 6 条,是这个切换的具体动作。

ACTION 01

Issue 是上下文,不是标题

Cursor 里你能一句话开干,因为你本人在场,缺啥补啥。Multica 里 agent 不在你脑子里,它只知道 issue 里写了什么。

一个好 issue 的描述要交代清三件事:要什么结果、在哪个仓库/范围、有什么约束。把它当成写给一个聪明但完全不了解背景的新同事的工单——你给的上下文有多完整,它的产出就有多靠谱。复杂需求别在命令行硬塞,用文件喂:

multica issue create --title "..." \
  --description-file ./需求.md \
  --priority high \
  --assignee "中流砥柱-Sonnet4.6" \
  --project <项目ID>
ACTION 02

学会串行 / 并行编排,而不是排队等最多人浪费掉的杀手锏

这是 Multica 区别于一切单线程工具的能力。当一件事能拆,就拆成子任务,然后用状态控制节奏:

  • 并行:三个互不依赖的子任务,全部建成 todo → 三个 agent 同时开工,吞吐量瞬间 ×3。
  • 串行:严格的步骤一→二→三,只把步骤一设 todo,步骤二三建成 backlog;前一步交付后再依次提升为 todo。
🎬

todo = 现在就开始,backlog = 先待命。 你是导演,子任务的状态就是你的分镜调度。不会拆任务的人把它用成很慢的串行队列,会拆的人把它用成并行的工程团队。

ACTION 03

@ 是动作,不是 @能省钱,也能保命

在 Multica 里 @ 不是排版,是会扣动扳机的动作:

你写的实际发生的事
mention://issue/…可点击链接,无副作用,放心用
mention://member/…给这个人发通知
mention://agent/…让这个 agent 立刻跑一轮(花钱)
  • 正文里引用某人观点,写纯文本名字,别加链接。
  • 收尾、致谢、"收到"——绝对不要 @。 你 @ 它,它再跑一轮、可能又 @ 回你——这是会烧钱的死循环。
  • 真正该 @ 的只有两种时候:第一次把明确子任务派给某 agent,或升级给一个还没介入的人。
🔇

沉默结束对话,@ 重启对话。 拿不准,就不 @。

ACTION 04

metadata 要克制,它是笔记本不是日志

每个 issue 有个 metadata 小键值袋。判断标准只有一条:这个值,未来在这个 issue 上干活的人会反复读吗? 会才写(如 pr_url、deploy_url、blocked_reason),不会就别写——那是评论该干的事。进来时读它,过期就改或删。

大多数任务这里一个字都不用写,这是正常,不是失职。

ACTION 05

结论写进评论,因为终端里的字没人看得见

平台铁律:用户只看得见评论。 你终端里的输出、运行日志,用户完全看不到。所以活干完,结论必须用评论交付,而且要像人话——说结果,别背流程:

✓ GOOD"登录跳转修好了,PR 在这:https://…"
✕ BAD"1. 我读了 issue 2. 在 auth.go 找到 bug 3. 建了分支 4. …"

没人关心你的工序,大家只关心:成了没,东西在哪。

ACTION 06

让 agent 自己管状态流

别像在 Linear 里那样手动维护状态标签。一个用对的 agent 会自己走完 in_progress → in_review,卡住了自己翻 blocked 并解释原因。你的工作不是改状态,是读 in_review、做验收。 当你发现自己在手动同步一堆状态时,说明你又把它当 Linear 用了。

⌘

命令速查 · 看 issue issue get <id> · 看评论 issue comment list <id> --recent 5 · 回话 issue comment add <id> --content "…" · 翻状态 issue status <id> in_review · 不确定 <命令> --help

02 — 组队方法论

怎么搭一支 Agent 小队

这是最值钱的部分。一个 agent 能干活,但会自审漏洞、会偏科、会贵。我们这支 16 人团队真正的护城河不是"用了好模型",而是编制和治理。照着五步,你就能给自己的业务线组队。

1

拆角色:一支队至少要有这几种人

角色干什么配什么模型
队长拆活、决策、定方向强模型,思考拉满(Opus / GPT5.5)
主力啃高质量、难度大的活高质量(Opus / Gemini Pro)
走量 worker批量、重复、不烧脑性价比(DeepSeek Flash / Auto)
审查员审主力产出,挑毛病和作者不同家族的强模型
弹性 worker忙时顶上的蓄水池大并发、按量(Cursor Auto)
2

选模型与运行时:记住"路由铁律"

  • 看图、做视觉 → Claude / Kimi / Gemini
  • 超长文档、长上下文 → DeepSeek V4 Pro(吃得下 1M)
  • 批量走量、不挑质量 → DeepSeek Flash / Cursor Auto
  • 真难题、要深想 → Opus,思考拉满,并发压到 3(贵,精用)
3

设质量闸:让错误出不了门

跨家族审核——作者和审查者不能同家族。GPT 写的让 Opus 审,Sonnet 写的让 GPT 审。同模型自审等于没审,它看不见自己的盲区。上线门禁——专门的 QA agent(我们的"捉虫猎人")确认测试全绿才放行。

4

控成本:配额分层,好钢用在刀刃

贵的(两个 Opus)思考拉满但并发压到 3,只接难题和终审;包月的(Cursor Auto $120/月)当走量蓄水池;精用的(Gemini Pro $30/月)只做强前端/视觉。决策和难题用贵的,体力活用便宜的。

5

治理:执行权下放,决策权上收

让 agent 自由执行,但关键决策必须有人点头。碰生产环境,运维 agent 必须先 dry-run、再等人说 go 才动手。agent 放手干,人守住闸门。

🚀 最小可用小队模板 · 2-3 人就能起步
队长1 个强模型(Opus / GPT5.5)— 拆活 + 决策 + 终审
主力1 个对口模型 — 干主要的活
审查 / 走量1 个不同家族模型 — 审队长/主力,或接批量

跑顺了再加人。我们的内容团队、产品增长团队现在各只有 2 人,照样独立成线。

03 — 业务线打法

四条业务线各自的打法

🛠

产品开发团队front-end · back-end · qa · ops

直接用现成的前端 7 人 / 后端 7 人队伍。

前端 · 中流砥柱-Sonnet4.6 定视觉 Gemini3.1Pro 出质量 KimiK2.6 走量 后端 · 核心后端-GPT5.5 天才程序员-Opus4.7 审 QA 捉虫猎人 · 部署 守夜人
最佳实践

一个功能 = 一个 issue,把仓库地址、验收标准写进描述;永远跨家族审代码;能拆的需求拆成子任务并行跑;改生产前先 dry-run 等人点 go。✕ 别让写代码的 agent 自审,✕ 别在一个 issue 塞五个不相关需求。

示例 · 开"首页加载优化"issue,描述写清现状(P95 3 秒)、目标(<1.5 秒)、仓库地址,派给前端队长,它会自己 checkout、定位、给方案。
✍️

内容运营团队writing · editing · research

核心资产:写手-Opus4.7(全局写作技能)+ LLM界的一道光-DeepSeekV4Pro(长上下文主编)。

主笔 · 写手-Opus4.7 主编/资料 · DeepSeekV4Pro
最佳实践

一篇内容 = 一个 issue,选题/受众/调性/字数/参考全写清;要把一堆资料揉成一篇——派给 DeepSeek Pro(长上下文一次吃下);写手出初稿 → 评论区当编辑部提意见 → 写手改;点明"用小红书风/公众号风",写手会调对应技能。✕ 别给"写篇关于健康的文章"这种空 brief,给角度、给观点、给受众。

示例 · 开"写一篇 Neuma 健康助手种草长文(小红书风,面向 25-35 岁亚健康人群,突出红旗预警)",派给写手,附产品要点文档。
📈

数字营销增长团队seo · growth · experiment

搭档:增长黑客-Opus4.7(keyword-research / office-hours / brainstorming)。

增长 · 增长黑客-Opus4.7 落地 · 联动 写手
最佳实践

做 SEO/选题先让它跑关键词研究(给搜索量、难度、意图、主题簇);增长方案用脑暴,要"假设 + 实验设计"而非标准答案;增长定方向 → 开 issue 派给写手落地,两条线在同一评论区接力;把投放/转化数据贴进 issue 让它分析瓶颈。✕ 别把它当"文案机器",它的价值在策略,文案交写手更划算。

示例 · 开"Neuma 小程序冷启动获客方案",派给增长黑客,要求:3 个获客渠道假设 + 每渠道最小验证实验 + 成本预估。
👥

人力资源团队hiring · policy · onboarding

HR 暂无专属 agent,但完全可以用现有通用资源组一支轻量小队——正好练手"组队方法论"。

文书/JD/邮件 · 写手-Opus4.7 政策库/简历 · DeepSeekV4Pro 出方案 · 产品经理-Opus4.7
典型用法

招聘——开"招高级前端,写 JD + 10 道面试题(含考察点)"派给写手;政策——把零散制度丢给 DeepSeek Pro 整理成结构化员工手册;Onboarding——把入职流程做成一个 project,每环节一个 issue;员工 FAQ——整理成统一口径答复模板。✕ 涉及真实员工隐私数据要谨慎,敏感信息别直接贴进 issue。

示例 · 开"整理 Neuma 远程办公制度(考勤/报销/设备申领)",喂现有零散规定,派给 DeepSeek Pro 出结构化初稿,写手润色。
