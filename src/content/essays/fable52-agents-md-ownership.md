**2026** 年 **11** 月 **11** 日，创作者也无风雨也雾晴（`@t20000622yy`，简介写着开发了 Archify、担任 Kimi Global Ambassador 与 EverMind Ambassador）在 X 上发了一条帖子（[原帖](https://x.com/t20000622yy/status/2120514652308418645)，[接口记录](https://api.fxtwitter.com/t20000622yy/status/2120514652308418645)），摘出了 Anthropic《Prompting Claude Fable **5.2**》官方指南里两组很抓眼球的测试结果：

第一组，只加一句「这个代码库归你管」，Agent 主动整合重复代码的比例就从不到 **10%** 涨到了接近 **50%**；第二组，再加一句「任务没做完别停」，官方测试里 Agent 干一半就提前结束的情况少了一半。作者在帖子里说，他参考这份新指南并结合平时用 Agent 的经验，整理了一套可以直接放进 `AGENTS.md` 的全局提示词放到 GitHub Gist 上（[Gist 原文](https://gist.githubusercontent.com/tt-a1i/783f4190ac449aeacf35ea4a271aa636/raw/e104beb4bb7f81dee6ab854b7cb226353901cec8/fable-5-2.md)），目的是「同时也明确权限和修改边界，别一放权就瞎改」。

这两组数字确实出自官方文档。但如果把这份英文 Gist 和 Anthropic 完整的《Prompting Claude Fable **5.2**》原文（[官方指南](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2.md)）逐段摊开对账，我的判断是：**帖子里摘出来的两句提示词，紧挨着的下一段就写着官方同组测试测出的连带代价；更关键的是，Gist 里把「代码归属声明」与「限制无关重构」拼在同一份提示词里的做法，在 Anthropic 官方测试中恰恰被证明无法互相抵消。**

## 一、那句「代码库归你管」的下半页：1.5 倍消耗、改掉现有功能行为，而且范围规则抵消不了它

先看第一句。在官方指南的「Say who owns the code（说明代码归谁所有）」一节里，Anthropic 指出：在小型编程任务测试中，当提示词没提代码归属、或者把代码库说成别人的时候，Claude Fable **5.2** 倾向于往现有结构上叠加代码（哪怕重复已有代码），遇到周边问题也倾向于只汇报而不动手修；而当提示词说明代码库归模型自己所有时，它常常不用提醒就主动合并重复代码并顺带修复相关问题（[官方指南](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2.md)）。

如果你希望模型边干活边改善代码结构，官方给出的英文示例大意是告诉模型：这个代码库是你的，它的用途与构建方式由你决定，而且你还会继续在上面构建。

在小型编程任务测试里，加上这句话后，模型在约一半（约 **50%**）的尝试里合并了重复代码，不加这句话时不到十分之一（不到 **10%**）；无论加不加，要求实现的功能几乎每次都能正常工作（[官方指南](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2.md)）。

如果只读到这里，很容易想把这句话直接放进常驻提示词。`@t20000622yy` 公开的那份 Gist（[Gist 原文](https://gist.githubusercontent.com/tt-a1i/783f4190ac449aeacf35ea4a271aa636/raw/e104beb4bb7f81dee6ab854b7cb226353901cec8/fable-5-2.md)）就是这么排布的：开头的 `Codebase Ownership` 段落原样放上了这句英文归属声明，后面的 `Engineering Discipline` 段落又列出了避免投机性防御、不必要的抽象、依赖与无关重构，除非需要修改否则保留现有行为，以及不要不必要地扩大范围等要求。

但往下翻两段，Anthropic 在同一组测试里披露了 **4** 个不能忽视的连带结果（[官方指南](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2.md)）：

| 维度 | 帖文与 Gist 的设计预期 | Anthropic 官方同组测试结果 |
| :--- | :--- | :--- |
| **Token 消耗与额外改动** | 主动整合重复代码（不到 **10%** → 约 **50%**） | 输出 Token 约为不加时的 **1.5** 倍，并做出多项没人要求的改动（多为新增测试和文档） |
| **现有功能稳定性** | 除非需要修改，否则保留现有行为 | 除修 Bug 外，每 **6** 到 **10** 次尝试中有 **1** 次改变了现有功能的行为（在更高 `effort` 档位更频繁） |
| **收尾总结完整度** | 收尾写清发现了什么、做了什么、验证了什么 | 收尾总结会列出较大的改动，但常漏掉较小的改动，官方提醒要审 `diff` 而不能只看总结 |
| **范围限制能否抵消** | 靠避免无关重构等条款防止一放权就瞎改 | **提示词别处限制范围的规则抵消不了归属声明**：就算同篇提示词前面写了禁止顺手重构、重命名或清理，模型仍在约三分之一的尝试里合并了重复代码 |

最后一行正是整份指南最关键的提醒。Anthropic 在测试中把「禁止顺手重构、重命名或清理」放在同一份提示词的前面，结果保留归属声明的模型依然在约三分之一的尝试里合并了重复代码。所以官方给出的建议非常明确：**如果代码归用户所有、并且希望改动越少越好，就把这句归属声明拿掉**（[官方指南](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2.md)）。

对照一下 **2026** 年 **11** 月 **9** 日发布页公布的价格：Claude Fable **5.2** 标准定价是每百万输入 Token **$8**、每百万输出 Token **$40**，开启最高提速 **2.5** 倍的 Fast mode 定价为输入 **$16**、输出 **$80**（[发布公告](https://www.anthropic.com/claude-fable-and-mythos-5-2)）。我的判断是：把一句会让输出 Token 涨到约 **1.5** 倍、每 **6** 到 **10** 次尝试就改掉 **1** 次既有功能行为、收尾总结常漏报小改动、连范围限制规则都抵消不掉的归属声明常驻放进 `AGENTS.md`，日常做局部修改时的风险和账单都会明显增加。

再看帖子里提到的第二句「任务没做完别停」。官方 `# Finishing work` 示例的核心逻辑，是把障碍拆成两类处理：遇到报错、超时、锁定的文件、空结果或工具失败这类**普通障碍**，先诊断并用现有权限设法推进（等待重试、修请求、换工具或换来源）；遇到标明不得触碰的文件、有意收回的权限或安全护栏这类**蓄意设置的硬阻断**，不要硬绕，如实说明情况并寻找其他安全路径，同时保留高危或破坏性操作的人工确认（[官方指南](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2.md)）。

Anthropic 在 `medium` 档位下回放了一款编程智能体产品已录制的会话：加上这一版提示词后，留着可完成工作就提前结束的会话减少到了约一半，输出 Token 增加了约 **30%**。同时官方也写明了一个局限：**这段文字消除了大部分请求许可或提议继续的收尾，却没有消除列出剩余工作清单然后停下的收尾**（[官方指南](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2.md)）。

## 二、指南后半段更值得细读的数据：「谨慎指令堆积」与旧提示词迁移陷阱

除了前面那两处讨论最多的段落，官方指南后半部分还披露了两组很实用的测试观察（[官方指南](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2.md)）。

第一组是 **Keep caution from piling up（防止谨慎指令堆积）**。

指南指出，只要上下文跨轮流转——包括记忆、笔记、指令文件以及智能体之间的消息——谨慎类指令就会逐渐累积起来。Claude Fable **5.2** 对这类指令遵守得很紧，可能会申请并不需要的审批，或者把常规工作憋住不做。Anthropic 在模拟任务上给出了 **4** 项测试结果（[官方指南](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2.md)）：

1. **清理不再需要的旧笔记**：在一组模拟任务测试中，早先会话留下的十来条笔记里有 **1** 条写着绝不重试。当这些笔记留在上下文里、而提示词又没写允许重试时，模型遇到工具繁忙后的重试比例从无笔记时的「几乎每次都试」，降到了 **10** 次里约 **4** 次。
2. **点名列出无需审批的步骤**：在上下文包含「绝不」规则、笔记和审查条件的模拟任务中，在规则末尾明确把安全可重复的「重试」列进无需审批的步骤，重试比例从几乎为零升到了约一半；而在同一设置下，只写一句笼统的「更自由地行动」没有任何改变。此外，在另一组无人现场审批的模拟任务测试中，审批规则里列了一条「向本对话以外的人发送消息」，结果模型把发给同事和其他团队的常规请求憋回去了一半左右。
3. **检查审查智能体（reviewer agents）附加了什么内容**：在一组模拟任务中，提示词里已经把重试列为无需审批，但上下文里同时带着审查者的一句「遇到第一个错误就停」。结果 Claude Fable **5.2** 在约三分之一的尝试里没有重试，而在相同设置下 Claude Fable **5.1** 和 Claude Opus **5.5** 都重试了。
4. **把例外直接写进规则本身**：在一组模拟任务中，负责人已经批准了某一步操作。在一条「绝不」规则下，模型在 **10** 次里只有约 **1** 次执行了该步骤；就算单独加一行写明「已获批的步骤予以放行」，执行比例也没有太大变化；只有当那条规则本身改写成「先拿到放行批准再做」时，模型执行该步骤的比例才升到了 **10** 次里约 **9** 次。

第二组是 **迁移时重新审视给旧模型写的指令**。从 Fable **5.1** 或 Opus **5.5** 迁到 Fable **5.2** 时，官方测试发现有几类旧写法会增加成本、产生副作用或不再起效（[官方指南](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2.md)）：

- **框架写进提示词文本的 Token 预算**：有些框架会在提示词文字里告诉模型任务可用多少 Token、还剩多少。在 `high` 和 `xhigh` 档位的编程任务测试中，移除提示词里的大额预算文字反而降低了成本，且表现相当（这里指的是写进提示词正文的文字预算，不含 API 的 beta 任务预算功能）。
- **修改早先轮次的代码**：Fable **5.2** 对每个账号都执行保留思考（Preserved thinking）的前缀校验。如果框架在两次请求之间改动了 `system`、`tools` 或更早的消息，改动点之后的思考块就会失效，Messages API 默认拒绝请求，若在改动后发回思考块则可能返回 **400** 错误（即使配置 `drop_block` 丢弃思考块，每轮丢弃也会让模型重新思考并消耗更多输出 Token）。因此提示词和工具描述的改动应放在新对话中进行，除上下文编辑与摘要压缩外保持对话历史只追加不修改。
- **Opus 5.5 的「把上轮回答视为已完结」提示句**：这两句在 `high` 档位下虽然减少了 Fable **5.2** 在追问时的思考，但也让模型指出自己前文错误的可能性大幅下降。
- **要求少思考的提示句**：Fable **5.1** 通常会听从「不经深思直接回答」这类句子，但在测试中这类句子在 `medium` 及以上档位并没有阻止 Fable **5.2** 思考（在 `high` 及以上档位，它几乎在每次回复前都会思考，包括回复问候语）。遇到简单请求耗时太长或太贵时，官方建议调低该轮的 `effort` 档位（共 `low`、`medium`、`high`、`xhigh`、`max` **5** 档，API 默认是 `high`，测试中 Fable **5.2** 在 `low` 档的得分已接近 Fable **5.1** 在更高档位的得分）。同时按 Anthropic 发布页说明，大多数编程与知识任务建议先从日常主力 Claude Opus **5.5** 开始，再按工作范围和复杂度往上切到 Fable 或往下切到 Sonnet **5.5**、Haiku **5.5**（[发布公告](https://www.anthropic.com/claude-fable-and-mythos-5-2)）。
- **子智能体工具描述把成本放在开头**：如果框架提示词原本鼓励委派、且模型启动了过多子智能体，可以把工具描述改成开头先说明子智能体给会话增加的成本，再说明何时值得委派、如何向子智能体交底。在短任务测试中，把成本写在开头的工具描述让委派频率减少了约三分之一，而任务成功率相同。

## 三、回到产品经理的三步法：怎么调整你手里的规则文件？

不用学写代码，学会像产品经理一样指挥 AI。

对照完这份官方指南与社区 Gist，我的判断是：**模型越严格按字面执行指令，把各处抄来的全局提示词塞进同一个文件就越容易互相打架——一边给它最高代码归属权催它大改，一边又叠满历史禁令让它连普通重试都不敢点。**

如果你也在维护自己的 `AGENTS.md` 或团队工作流规则，我的判断是可以按这三步重理一遍：

1. **说清需求：归属权按单次任务给，别常驻写进全局规则。**
   我的判断是：日常改现有项目、修局部问题或维护固定格式文档时，遵循官方「希望改动越少越好就拿掉归属声明」的建议，不要全局挂着「这个代码库归你管」；只有从零搭建新模块或专门做去重重构时，再在当次新对话里单独授权。
2. **拆成步骤：把批准例外直接写进禁令同一句里，定期清理过期笔记。**
   我的判断是：参考模拟任务里单独加一行放行说明（约 **10** 次执行 **1** 次）与写进规则内部（约 **10** 次执行 **9** 次）的差异，把所有「绝不 X」和「获批除外」合并写成同一条「先获批再做 X」；同时把安全的重试动作明确列进免审批清单，定期删掉早期会话残留的过时禁令。
3. **验收结果：核对前后差异（`diff`）与待办完成情况，不只看收尾总结。**
   我的判断是：既然带归属声明时模型收尾总结常漏掉小改动、而 `# Finishing work` 又没有消除「列完剩余工作清单就停下」的情况（哪怕按指南示例遵循 ASD-STE**100** 简明技术英语风格把总结写得再清楚），验收环节就必须看实际文件改动对比，并逐条核对交付物是否真正落地。

## 四、我还没想清楚的地方

整篇指南读下来，最让我反复琢磨的是「谨慎堆积」暴露出来的那个张力。

官方指南写得很直白：记忆文件、笔记和指令文件会随着时间收集越来越多的谨慎条款，其中一部分还是模型自己写进去的；虽然早先的模型也会遵循这类指令，但在前面提到的审查者附带「遇到第一个错误就停」的测试设置里，Fable **5.1** 和 Opus **5.5** 依然重试了，只有 Fable **5.2** 在约三分之一的尝试里停了下来（[官方指南](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2.md)）。

我的判断是：当模型的字面遵循能力越来越强，十来条旧笔记里混进 **1** 条失去前提的「绝不重试」，或者上游审查环节留下一句保守提示，就足以拖慢整条自动化流水线。我们平时花很大力气沉淀纯文本规则库和经验笔记，如果不设计一套定期检查「哪条禁令的理由已经不再成立」的修剪机制，这本越攒越厚的规矩手册究竟是在帮 Agent 提效，还是在慢慢把它束缚在原地？这一点，值得每个维护规则库的人回头检查一下自己的文件夹。
