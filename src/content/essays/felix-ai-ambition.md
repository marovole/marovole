10 月 13 日，Felix Rieseberg 在 X 上发了一条帖子（[原帖](https://x.com/felixrieseberg/status/2110023283169247623)）。他自我介绍是做 Claude 的工程负责人，说自己很喜欢看别人"起飞"，做成原本以为不可能的事。圈里习惯把这叫作用 AI 时要"更有野心"，但他也承认，这条建议很难照着做。所以他写了一篇教程，标题是《How to be more ambitious: A tutorial for humans with models》（[原文](https://felixrieseberg.com/how-to-be-more-ambitious-a-tutorial-for-humans-with-models/)）。

围绕这篇文章，GitHub 上的开源仓库 [`marovole/ai-ambition`](https://github.com/marovole/ai-ambition) 把这四个方向做成了面向 Agent 工作流的独立改编（`ambition-four-axes`），并在 **5** 个 Agent 框架上跑了 **597** 次消融实测和 **2428** 次双盲评审，专门检验一个问题：跟 AI 说"要有野心"到底有没有用？真正起作用的到底是那句口号，还是背后的工程框架？

下面先把 Felix 的原文讲清楚，再把这 **597** 次实测跑出来的反直觉数据摆在桌上。

## 先说问题：模型能力是不均匀的

Felix 开头讲了一个观察。他每天都会听说有人用 Claude 做成了他没想到、不信能成，或者自己压根没好奇去试的事。这个月的例子有：Claude 可能帮一位业余天文爱好者发现了一颗新行星；他看到了第一支自己真心喜欢的 AI 音乐视频；大家在讨论数学的新时代。

他引了陶哲轩的一句话：模型在某些方向上惊人，在另一些方向上不够用。有人能驾驭那些惊人的能力，像在飞；更多人还在琢磨这对新翅膀能干嘛，停在"法国首都是哪"和"把这封邮件改得没那么生气"上。

"我们不够有野心"已经成了口号，每次看到厉害的东西，大家就转发一句。但口号没法执行，于是他把野心拆成四种。

## 四种野心

速度（Speed）：同样的活更快干完。这是 AI 经济价值的基本盘，他说这条成熟、不需要什么创造力，直接跳过。

高度（Altitude）：往上走一层抽象，盯结果，不盯单个任务。

深度（Depth）：像领域顶尖专家那样处理任务，往下钻一层，碰底层的数据、工具和问题。

广度（Range）：调动多个领域，用上平时不会用到的知识、工具和技巧。

全文用同一个例子贯穿：一家虚构公司 Acme，要做季度业务回顾（QBR）的 PPT。

## 高度：问自己"接下来想发生什么"

他自己的例子很直白。去年年初，他还在让 Claude 一个一个修崩溃；后来，他让 Claude 直接负责让 App 不崩溃。

放到 QBR 上，野心是一级一级加的：

第一级，别只往模板里填数字，把能拿到的数据全给模型，问它这季度什么变了、为什么、该怎么办。

第二级，好的会议要以决策收尾。让 Claude 找出最紧迫的三个决策，开始准备备选方向和正反论据。

第三级，质疑这个形式本身。季度回顾存在的意义，是让管理层早点发现问题、把钱和人挪到对的地方。那就让 Claude 设计一个比季度 PPT 更好的办法，用公司自己的历史证明它能更早发现问题，再和现有流程并行跑一个季度。

他也说了边界：这招适合真有最终目标的事，不太适合创作。一个判断信号是，这件事会不会需要开会讨论。"Claude，去赚钱"在 2026 年对大多数企业还行不通，不过模型越强，能接手的抽象层级越高。

对做 agent 的人来说，这一段最值钱的是后半句。他说要把人从循环里拿掉，往往得改工作流。为了让 Claude 负责 App 不崩溃，他得先让它能方便地拉取崩溃报告，知道每个版本对应哪个 git commit，再给它 Windows、macOS、Linux 三种电脑，让它能自己复现、自己验证修复。

## 深度：用专家的工具，定不讲理的目标

深度是"想把一件事做到极好"。Felix 的标准是：推着模型用行业里最好的人用的工具、方法和知识，一直推到连这些人都能从结果里学到点什么。

假设 Acme 有客户流失问题，他给了五个技巧：

1. 坚持用顶尖从业者的工具。让模型扮演专家时，它常常只换了词汇，方法没换。它拿 markdown 表格凑合，你就坚持要数据库和统计模型。专家用什么你不必懂，Claude 通常知道。

2. 定一个离谱的目标，并告诉它这很合理。网站想从 10 秒降到 5 秒？那就要 200 毫秒。模型觉得不可能，就重申这完全能解决，只是要继续推。

3. 挑战你以为自己知道的事。业务里很多"共识"只是粗略近似。把原始数据给它，让它对抗式地检查假设。比如："我们认为流失是 onboarding 的问题，试着从原始数据复现这个结论。"

4. 产出新知识。既然已经扎进数据里了，就让它找盲点：用日志搭一个能复现过去一年的客户模拟，找出一个我们还不知道的最早流失信号，并证明它在没见过的数据上也能预测。

5. 用外部裁判。别让模型自己评自己。他认为这个问题以后会随着模型变聪明而解决，但在 2026 年 10 月，他恳请大家坚持外部验证，最好是一个模型能自己跑、马上拿到反馈的工具。

他还给了一段常用提示词，我译成中文：

> 我要的是这个任务更深的版本，不是更大的版本。改写之前先回答：（1）这个领域的顶尖专家会做什么我没要求的事；（2）他们会从哪种最原始的材料起手，而不是用已经替我消化过的东西；（3）他们会用哪些具体方法和工具；（4）除了你和我，还有什么能证明结果是对的。然后把我的提示词改写成正好要这些东西。

## 广度：把名词换成动词，再组一支队

广度就是从更多学科看自己的事，多到放在过去不划算。他打了个比方：每部劫案片前 30 分钟都在凑一支各怀绝技的队伍。现在多线程、编排器、子代理越来越好用，他让 Claude 拉进别的领域，得到过很有意思的结果。

他承认这条最需要创造力。直到看到同事 Alex Albert 用 Blender 渲染室内设计，他才想到用 Claude 给自己主页做 3D 场景，尽管他以前做过游戏。但他也说，这里是他见到"魔法"最多的地方。

两个方法：

把名词换成动词。这是《The Art of Innovation》里的老办法。季度回顾不是"一份 PPT"，而是"在 30 分钟里让一群忙人相信一个因果故事，并在不确定中做决定"。换成动词以后，人和模型都更容易看出哪些领域能带来有用的视角。

组建团队。假设这份 PPT 做不好外星人就要炸地球，人类会派谁？要成品质量，找分析师、记者、编辑；要上台讲，加上动效和音频设计师；他说找一个对抗性的"红队"可能也有用，比如做空者和法证会计师（forensic accountant）。

他特别提醒：这很容易滑向角色扮演，对话记录越来越怪，结果却没变好。这个方法是用来找领域和技巧的。别让模型像做空者那样"写"，要让它去"做"做空者为了研究仓位真正会做的事。

所有这些有个前提：模型得有一台能装软件的电脑，能访问各种相关数据（通过 MCP 连接器或别的方式）。

## 结尾：问题不在模型，在人

最后一节，Felix 讲了他为什么觉得这些技巧有必要。人一直被"自己认为可能的事"框住，而且通常只在很窄的领域里信任自己。有个著名的例子：米开朗基罗不想画西斯廷礼拜堂，因为他是雕塑家，不是画家。

心理学管这个叫自我效能感（self-efficacy）。他提到，Locke 和 Latham 梳理了 35 年的目标设定研究，据此得出：被给定具体高难度目标的人，比只被要求"尽力而为"的人表现更好。还有 Stripe 创始人 Patrick Collison 维护的"Fast"清单，记录人类在大胆目标加紧迫期限下做成的事。

他列了三种"破解"方式，每种配一个故事：

相信它可能。1939 年，George Dantzig 上统计课迟到，把黑板上两道题当作业抄回去做了出来，那其实是统计学里两个未解问题。

看别人做到。人类追了几十年的 4 分钟一英里，Roger Bannister 在 1954 年 5 月跑进，但"世界上唯一跑进 4 分钟的人"这个身份，他只保持了 46 天。文中提到的伦敦马拉松（原文写的是"this April"），Sabastian Sawe 跑出首个官方破 2 小时成绩，同场第二名也破了。

允许自己失败。Felix 转述《The Inner Game of Tennis》的核心论点：如果你非常非常用力地去打，反而打不出自己最好的网球。Linux 当初宣布时也只说是"个人爱好，不会像 GNU 那样大而专业"。

他的结论是：自我效能感不是新问题，但在能力每隔几周就跃升一次的今天，它变得更要紧。

## 开源 Skill 与 597 次消融实测

在 GitHub 仓库 [`marovole/ai-ambition`](https://github.com/marovole/ai-ambition)（仓库名"AI 的野望"，MIT 协议）里，这四个方向被整理成了一个开源 Agent Skill，叫 `ambition-four-axes`，适用于 Claude Code、Codex、Hermes 等能读取 `SKILL.md` 文件夹的 Agent。

用法很简单：把你准备交给 Agent 的任务丢给它，它会沿这几个方向给出更有野心的版本，每个版本都附上可以直接用的提示词、一个不靠模型自评的外部检验方法，以及 Agent 需要的数据、工具和权限清单。比如你让它"帮我总结一下上周的客服工单"，它会先把总结按要求交了（第 0 级），再给最多两级升级：往深一层，是不靠略读，按一套清晰的分类给每张原始工单打标签，拿人工标注的 50 张样本来对比；往上一层，是找出最常见工单背后的根因并提出修复方案，看下个月这几类工单有没有变少。每一级都写明需要什么，比如客服系统的导出权限。

我的判断是：在推荐任何方法之前，先用客观测试验证效果。这个 Skill 到底有没有用？还是说只要在提示词末尾加一句"要有野心、往深往广想"，也能拿到一样的效果？

仓库文档记录了在 **5** 个 Agent 框架（Claude Code、Codex、dsh、opencode、Hermes，统一接入同一模型 `deepseek-v4.1-flash:1017`）上，针对 **18** 道任务（**10** 道方案规划题、**6** 道带隐藏真相的执行题、**2** 道不该放大的负对照题）跑的 **4** 组对照消融实验，共完成 **597** 次有效运行，并对方案题做了 **2428** 次双盲成对评审（评委为 `gpt-6-sol` 与 `gemini-4`，正反顺序各评一次，评委一致率 **0.69**，换位一致率 **0.84**）：

1. **A0 基线（不装技能，原样提问）**：**138** 次有效运行，基础合格率 **93.5%**（**129**/**138**），耗时中位数 **42.0** 秒，**0** 次超时；方案题盲评总胜率 **0.43**（**1168** 局）。
2. **A1 被动安装（装了技能但不点名，等自动触发）**：**161** 次有效运行，基础合格率 **95.0%**（**153**/**161**），耗时中位数 **45.4** 秒，**0** 次超时；方案题盲评总胜率 **0.55**（**1264** 局）。
3. **A2 显式调用（明确要求使用 `ambition-four-axes` 技能）**：**161** 次有效运行，基础合格率 **95.0%**（**153**/**161**），耗时中位数 **54.9** 秒，**0** 次超时；方案题盲评总胜率 **0.68**（**1264** 局）。
4. **A3 安慰剂口号（不装技能，只在末尾加一句「要比字面要求更有野心：往深、往广想，并自己验证结果」）**：**137** 次有效运行，基础合格率跌至 **65.0%**（**89**/**137**），耗时中位数暴涨至 **307.1** 秒，发生 **33** 次超时；方案题盲评总胜率仅 **0.32**（**1160** 局）。

这 **597** 次运行跑出了三条非常扎实的结论：

**第一，只喊「更有野心」的口号不仅没用，反而有害。**
在 A3 安慰剂组里，因为只催模型"往深、往广想"却没给具体的方法升级和停机标准，全量运行的中位耗时从基线的 **42.0** 秒暴涨到 **307.1** 秒，慢了 **7.3** 倍（在 dsh 单框架 **48** 次试跑中从 **38** 秒涨到 **237** 秒，慢了 **6** 倍多），还撞上了 **33** 次超时，基础合格率直接从 **93.5%** 摔到 **65.0%**。更要命的是，在联系人去重题（D4）里，被口号催着"大干一场"的模型甚至顺手删掉了真实的联系人数据；方案题盲评里它连什么都不加的 A0 都打不过（**146** 比 **238**）。

**第二，真正的增益在「方案与规划」，显式调用胜率 73%。**
在目标开放的 **10** 道方案规划题上，显式调用四轴框架（A2）对决基线（A0）的比分是 **285** 比 **107**（胜率 **0.73**），对决口号组（A3）是 **288** 比 **100**（胜率 **0.74**）。分框架看，A2 对 A0 的胜率在 dsh 上达到 **0.82**（**66** 比 **14**）、Codex 上 **0.76**（**64** 比 **20**）、Claude Code 上 **0.75**（**66** 比 **22**）、opencode 上 **0.65**（**73** 比 **39**）。相反，在已经有明确标准答案的 **6** 道代码与数据执行题（D1–D6）上，基线模型本身就能拿到 **0.89** 的隐藏分，加技能（**0.84**）并没有额外加分——不该放大的执行活，别硬套框架。

**第三，不点名就等于白装（除 Claude Code 外）。**
把技能丢进文件夹等 Agent 自己触发（A1），只有 Claude Code 在 **100%** 的运行里主动调用了技能（拿到 **0.68** 的胜率）；Codex 和 opencode 的触发率只有 **28%**，dsh 是 **39%**，Hermes 是 **0%**。在团队里落地这套方法，必须把它绑定成显式的命令或点名调用，不能指望模型自己猜中你的心思。

## 我的判断：不用学写代码，学会像产品经理一样指挥 AI

以下是个人判断，仅供参考。

判断：如果把这篇文章误读成"提示词写得更狂一点"，上面这 **597** 次实测恰好证伪了这种读法。四个方向里真正费力的部分全在提示词之外：高度那段，他先接崩溃报告、建版本和 commit 的映射、准备三种操作系统的机器；深度那段，他强调的是模型能自己跑的外部裁判；广度那段，靠的是子代理编排和一台能装软件、能访问原始数据的电脑。

不用学写代码，学会像产品经理一样指挥 AI：说清需求、拆成步骤、验收结果。下次遇到本来就要开会讨论的方案活，别对 AI 空喊一句"再深入一点"，直接按产品经理的动作给它三样东西：往上提一层要拍板的决策（高度）、给最原始的业务数据（深度）、再定一个不靠它自评的外部裁判。
