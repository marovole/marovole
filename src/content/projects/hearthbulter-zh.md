建 HearthBulter 源于一个具体的挫败感：健康数据被困在孤岛里。体检报告在一个 app 里，购物清单在另一个，营养师的建议在一个两个月没打开的 PDF 里。没有人把"你该吃什么"和"食物怎么进你家冰箱"这两件事连起来。

HearthBulter 是一个饮食引擎，读取你的健康基线——体检数据、可穿戴设备数据、或手动录入——翻译成每周食谱计划、料理步骤、以及一键下单的购物车。闭环的终点是食物到家。

## 我在解决什么问题

家庭健康管理有一个核心的协同失败：知道该吃什么，有解决方案；记录吃了什么，也有解决方案。但根据真实健康数据，自动把正确的食物送进家——没有人做到端到端打通。

## 我的角色

独立开发者和产品负责人。负责数据库设计、API 层搭建、AI 生成管道接入、以及部署上线（[healthbutler.life](https://healthbutler.life/)）。

## 关键决策

**71 张数据表，第一天就建好。**
健康数据是关系型的，不是平铺的。一份食谱计划链接到营养目标，营养目标链接到健康基线，基线链接到家庭成员，每个成员有各自的病史和饮食禁忌。早期项目的诱惑是把所有东西存成 JSON blob，"以后再说"。我抵住了这个诱惑。前期的 schema 复杂度在 AI 生成层体现了价值——LLM 拿到的是结构化上下文，而不是自由文本。

**Cloudflare Functions 而不是传统服务器。**
目标用户会在超市里拿着手机查食谱计划。Edge 部署意味着 API 从最近的数据中心响应。配合 Upstash Redis 缓存计算值（BMR/TDEE 不会每天变），移动端体验即便在负载下也明显更快。

**GPT-4 做食谱生成，而不是模板填充。**
早期原型用规则生成饮食方案——选蛋白质、碳水、蔬菜，完成。技术上正确，但食谱毫无生气。换成 GPT-4 之后，把结构化健康上下文注入 prompt，食谱开始根据季节、当地饮食偏好和冰箱库存动态适配。它像是被设计出来的，而不是被计算出来的。

## 已上线功能

- **健康入档**：录入体检结果、可穿戴数据或手动健康参数
- **AI 生成食谱计划**：7 天 / 30 天 / 90 天周期，附完整营养素分解
- **购物清单自动化**：计划一键转购物车，SKU 匹配电商平台
- **健康趋势可视化**：对照目标追踪实际摄入

## 我学到了什么

71 张表让我明白：数据模型的决策会复利。第一周建的表，约束了第十二周能做的事。如果重来，我会在写第一行应用代码之前，在 schema 上花更多时间。

从 AI 到电商的那一步是用户眼睛发光的地方。"点一下，食物就出现了"——这是产品的核心价值，在它之前的一切都是铺垫。
